# Take-2 bootstrap plan v0

## Goal

Build the smallest operating kernel that can execute one real research/backend workflow
with stronger recoverability, observability, diagnostic discipline, and lower control
surface than Reaserch.

## Non-goals

- reproduce Reaserch;
- migrate files because they exist;
- declare a final ontology before a vertical slice runs;
- promote experimental PD capabilities because they are interesting;
- create a registry when a typed view over kernel records is sufficient.

## Acceptance test

Take-2 must execute one vertical slice:

1. observe a bounded failure or research problem;
2. freeze and type the target;
3. run PD discovery/challenge;
4. preserve rivals and OPEN;
5. diagnose when the object is a failure;
6. select an authorized information-gaining or repair/research transition;
7. execute one transition;
8. verify protected behavior;
9. emit observations sufficient to reconstruct what happened;
10. re-enter PD when the result changes the represented problem.

Compare the slice with the legacy path on:
- durable surfaces touched;
- writes required;
- controls invoked;
- unsupported causal/authority claims;
- contradictions;
- manual recovery interventions;
- ability to reconstruct why state changed;
- latency where observable.

## Phases

### P0 Bootstrap
Create only charter, architecture, kernel schema, PD capability admission, experiment,
migration contract, and mechanical validation.

### P1 Vertical slice
Use a real low-risk backend/research case. No portfolio migration.

### P2 Adversarial review
Run HF-001, representation attack, clean-sheet rival, Multi-Object relation challenge,
A16, IC-018/RTC v2, and migration anti-rescue against the observed slice.

### P3 Capability admission
For each legacy capability choose REIMPLEMENT, IMPORT, REFERENCE, DISCARD, or OPEN.
Admission requires evidence of need in Take-2, not existence in Reaserch.

### P4 First project pilot
Only after the kernel slice passes. Choose a bounded project object; PD itself is not
migrated as a project merely because PD capabilities power the kernel.

## Recompute rule

After every material implementation step:
- freeze the changed baseline;
- rerun PD/IC challenge on the changed object;
- update the next highest-information step;
- preserve incomparable successors and OPEN;
- do not continue from a stale plan merely because this document says so.
