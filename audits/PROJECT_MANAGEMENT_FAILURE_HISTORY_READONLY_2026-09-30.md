# Cluster 1 — Canonical authority and source-of-truth failures

## Recurrent failures

- Newer artifacts were repeatedly mistaken for more authoritative artifacts.
- Artifact existence was repeatedly confused with artifact authority.
- Repository presence was repeatedly confused with migration completeness.
- Provenance was repeatedly confused with exact object identity.
- Current, historical, candidate, accepted, canonical, derived, and rejected artifacts were not always kept distinct.
- Multiple files carried partially overlapping authority, making it unclear which object controlled a field.
- A later summary or synthesis sometimes became the de facto source because it was easier to access than the actual source.
- Current-state summaries sometimes silently settled older unresolved questions.
- Historical or superseded architectures remained discoverable enough to be resurrected as though current.
- Exact individual page images were sometimes replaced in practice by PDFs, composites, previews, or regenerated candidates.
- A valid internal blueprint was repeatedly allowed to substitute for the requested author-facing or user-facing deliverable.
- Static human-readable registries drifted from canonical runtime/state registries.
- Tool names were treated as identities even when mathematics, configuration, runtime, invocation, run, receipt, and closure were different objects.
- Equal-looking structures were treated as identical because they had the same cardinality or surface shape.
- One giant control document was repeatedly asked to own too many mutable project objects, creating overwrite and conflation risk.

## Representative evidence

- ProjectManager lesson L002: later artifact cannot become authority merely because it is newer.
- ProjectManager lesson L003: one giant document causes overwrite.
- Tool System lesson L003: current-state file is a projection over retained history, not the history itself.
- Tool System lesson L004: name, math, configured identity, runtime, invocation, run, receipt, and closure are separate objects.
- PD retrospective: artifact presence vs artifact authority, provenance vs identity, repository presence vs migration completeness, completed repair vs stale closure state.
- Jewish Holiday Booklets: accepted individual PNG source sets vs PDFs/previews/composites/candidates.
- Canonical Authority: internal research/control blueprint repeatedly substituted for terminal author-facing outline.

# Cluster 2 — State, currentness, version, and freshness failures

## Recurrent failures

- No consistently authoritative current project state existed at several points in the history.
- State was split across human-readable summaries, structured state, project pages, manifests, registries, and conversation memory.
- Derived project pages became stale while the authoritative state had already changed.
- Fresh sessions could recover a legitimate but stale or superseded system version.
- Currentness pointers were not always synchronized after a real state transition.
- Static counts and indexes drifted after dynamic package admission.
- Closure states remained stale after repairs completed.
- Open coordinates were sometimes silently dropped during compression or handoff.
- A successful local run updated one surface but left dependent surfaces unchanged.
- Old prompts, summaries, or transfer documents could reintroduce superseded state.
- Project resumption depended too heavily on chat recency instead of durable state.
- A project could be managed correctly relative to an incorrectly recovered goal/state.
- Search/index state could become stale relative to repository contents.
- Accepted artifact identities were known but physical bytes were not yet in the expected repository location, creating false confidence about self-contained recoverability.
- Multiple PDF/document versions accumulated without a reliable currentness hierarchy.

## Representative evidence

- Backend Closure REAL_TASK_ENTRY_REGRESSION: Canonical Authority PROJECT_PAGE was stale in a result-sensitive coordinate while STATE.yaml was current.
- ProjectManager lesson L011: manager can manage correctly relative to stale or insufficiently recovered goals.
- Tool System lesson L007: dynamic parity updated, static counts/indexes drifted.
- ImprovementCore cross-chat root cause: current identity becomes stale; local repairs regress in fresh chats; OPEN state can be silently lost.
- Curriculum handoff history: approved PDF and regenerated source diverged; current-status and source-of-truth hierarchy were missing.
- Earlier PDF projects accumulated multiple reflowed/reconverted versions with unreliable pagination.

# Cluster 3 — Project entry, resume, handoff, and continuity failures

## Recurrent failures

- “Resume this project” did not reliably trigger repository/state recovery before answering.
- Conversation entry sometimes produced prose about the project instead of instantiating the current project packet.
- Canonical artifacts were not always displayed when visual confirmation was required.
- The system could know the correct current artifact and still fail to surface it.
- New-chat handoffs omitted current status, unresolved decisions, source-of-truth hierarchy, provenance, exact files, or initialization instructions.
- Handoffs sometimes contained revision history instead of a clean cold-start current state.
- Handoffs sometimes relied on external dependencies despite a requirement for one self-contained object.
- Accepted visual references were not always carried forward as exact continuity anchors.
- Cross-chat discoveries were not always durably captured.
- Material conversation events could disappear because capture triggers only fired for registered workstreams.
- A chat could switch topics or end before closeout, losing a material discovery.
- Project-specific continuation state existed, but there was no mandatory conversation-entry execution contract consuming it.
- User requests to “continue from where we were” sometimes caused reconstruction from memory rather than exact recovery.
- The user repeatedly had to re-identify canonical pages, files, prompts, or versions.

## Representative evidence

- IC008_PROJECT_ENTRY_ARTIFACT_RESUME_FAILURE: repository said the canonical Fick set controlled continuation/display, but the assistant answered with prose instead of displaying the pages.
- Conversation Capture Trigger Failure: capture controls existed, but substantive chats outside registered workstreams bypassed them.
- Curriculum/Erikson handoff history: missing current status, source hierarchy, unresolved decisions, reproducibility, and fresh-chat initialization.
- Sukkos booklet history: repeated need to visually verify the exact canonical four pages before continuing.

# Cluster 4 — Goal, scope, object, and semantic-definition failures

## Recurrent failures

- Load-bearing terms became operational before their type, scope, identity, or role was frozen.
- “Goal,” “road,” “spine,” “layer,” “tool,” “black box,” “coverage,” and similar terms carried multiple meanings.
- Projects sometimes moved into implementation before the exact object being improved was known.
- Project identity, research question, deliverable, and execution object were occasionally blended.
- Exploration was mistaken for project construction.
- Durable exploratory work was mistaken for authorization to create a full project package.
- A promising idea could trigger a project before the user had approved its highest-level identity.
- Research goals were sometimes conflated: hypothesis testing, exhaustive proof, novelty, publication readiness, and theoretical completeness.
- Architecture readiness was sometimes mistaken for artifact readiness, rendering readiness, or classroom readiness.
- Page correctness was mistaken for booklet correctness.
- Tool “coverage” collapsed domain, search, decomposition, execution, validation, runtime, and evidence coverage into one concept.
- “Black box” was used too early instead of first attempting reduction/type clarification.
- Audit scope changed while the audit was running, making closure unstable.
- Internal control architecture and final author/user deliverable were conflated.
- A one-page object, four-page set, contact sheet, four variants, and four separate pages were not always represented as different object classes.

## Representative evidence

- PD retrospective: semantic type erasure/failure to type control objects before relation, dependency, state, and closure analysis.
- ProjectManager L009/L010: no durable state between idea and project; exploration and project construction are different effect classes.
- New Tool Development Lessons L11/L12: checklist completion vs checklist completeness; black-box type too coarse.
- Canonical Authority whole-chat root cause: internal blueprint/author outline conflation.
- JHB image-generation audits: one page vs four pages; four pages vs four variants; page image vs contact sheet; revision vs fresh booklet; local repair vs regeneration.

# Cluster 5 — Planning, decomposition, sequencing, and replanning failures

## Recurrent failures

- A plan selected at state S0 was treated as still licensed after a material state change at S1.
- Work proceeded through prewritten multi-step plans without recomputing after result-sensitive deltas.
- “Next action” was treated as sufficient to determine “next method.”
- WBS/deliverable decomposition and schedule/temporal sequencing were conflated.
- Broad six-step or ten-step plans were sometimes executed as fixed scripts rather than adaptive routes.
- Routine project checks escalated into “run every tool” campaigns.
- Exhaustive verification was confused with ordinary orchestration.
- Backend repair work expanded until it risked blocking substantive work.
- Broad audits were repeatedly restarted when a new distinction appeared.
- Production was started before upstream specification, architecture, or source identity was stable.
- Batch production began before exemplar/quality gates were fixed.
- Work was sometimes organized around what was easy to generate rather than what the deliverable required.
- One-at-a-time production could be too slow, but attempted batching changed the object type instead of merely changing execution efficiency.
- Plans sometimes mixed work that was blocked with work that was independently executable.
- Unavailable external evidence sometimes held unrelated architecture work hostage.
- Local nonblocking debt was sometimes treated like a global project blocker.

## Representative evidence

- Fick adaptive production architecture: after every meaningful delta the plan needed recomputation.
- ProjectManager L005: WBS is not schedule.
- ProjectManager L012: exhaustive verification is not ordinary orchestration.
- Backend Closure reassessment: broad backend-repair mode had to be stopped once predictable repeated interruption was no longer a blocker.
- Curriculum production history: batch generation before architecture/exemplar/quality gate stabilization.
- Dinosaur image project: five-at-once generation degraded anatomical accuracy; one-species-at-a-time source-grounded iteration became necessary.

# Cluster 6 — Responsibility, ownership, and control-boundary failures

## Recurrent failures

- End-to-end activation responsibility was split across controllers, optimization layers, runtime authority, project-local systems, registries, and host behavior.
- A mechanism could exist without any object owning its full path from applicability trigger to execution to consumption.
- Shared infrastructure and project-local ownership boundaries were not always clear.
- Transfer/cross-project learning could bypass target-project authority.
- Candidate evidence was sometimes treated too close to admitted project state.
- Different objects could appear to own the same field.
- Project-level control coordinates were missing even while repository-level validation passed.
- Coverage documents were at risk of becoming semantic owners instead of evidence.
- Tool selection, execution, admission, mutation, and persistence ownership were not always separated.
- Delegation artifacts existed without evidence that delegated work actually ran.
- Historical and current controllers overlapped in discoverability.
- No single object guaranteed that a discovered reusable mechanism became enrolled, triggered, bound, executable, consumed, and verified.

## Representative evidence

- Tool Ecosystem Root Cause: split-control ownership and incomplete migration.
- Artifact-Without-System-Integration root cause: no owner for end-to-end mechanism activation.
- ProjectManager L004/L006/L008: coverage is evidence; tool result is evidence before admission; transfer preserves target authority.
- Tool System L009: project-level control completeness is its own regression surface.

# Cross-project root generators

The historical failures cluster around five deeper generators.

## RG1 — Representation is not authority, and authority is not execution

A project can contain the right idea, document, registry entry, or control and still fail because the system does not distinguish:
- represented
- current
- authoritative
- selected
- executable
- executed
- consumed
- verified
- persisted
- recoverable on reentry

Many regressions occurred between these states.

## RG2 — State was not fully externalized before action

When source identity, currentness, protected state, licensed delta, goal, scope, acceptance criteria, or dependency state remained implicit, the next session/tool/generator reconstructed them and introduced degrees of freedom.

## RG3 — No single mandatory transition path governed the whole lifecycle

The recurring lifecycle gap was:

discovery  
-> identity/type  
-> authority/currentness  
-> plan/selection  
-> execution  
-> result/receipt  
-> admission  
-> propagation  
-> persistence  
-> verification  
-> reentry

Different projects repaired subsets, but historical recurrence came from transitions being optional, split, or only declarative.

## RG4 — Local success was repeatedly mistaken for broader completion

Examples:
- one page vs booklet
- one test vs project
- repository pass vs runtime/host closure
- checklist completion vs checklist completeness
- same-basis fixed point vs global closure
- control audit vs artifact audit
- structural verification vs substantive verification
- semantic tool result vs executed tool
- preserved corpus vs promoted/current system

## RG5 — The user remained the final integration layer

When the system failed to carry authority, state, transitions, and verification across time, the user supplied the missing continuity manually.
