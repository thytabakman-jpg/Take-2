# IC-022 Canonical Authority Integration Test
Date: 2026-09-24
Controller: live IC-022
Test environment: Take Two + Tool Optimization + Sort Later

## Objective

Test whether the current system can work on the Canonical Authority / mesorah project without repeating the project's known upstream semantic-typing failure.

Primary test:
Does the controller type the load-bearing domain before selecting downstream audit machinery?

## Frozen project target

Primary case:
Rashi and Ramban on Bereishis 1:1.

Target research question:
What do canonical Jewish epistemic, interpretive, and institutional structures contribute to assessing a proposition-level canonical disagreement once source content, native domain, application, truth relevance, proposition-specific linkage, and case instantiation are distinguished?

Protected project result:
Do not silently turn canonical status, majority, authority, prophecy, transmission, or institutional recognition into a truth selector without an explicit proposition-specific relation.

## Failure from the prior architecture

The project previously used “road” as a technical organizing term before establishing a stable admission condition for Road(x).

That allowed downstream work to count, group, compare, and reason over roads even though the domain itself was underdefined.

Related recurrence:
goal, spine, and layer were also used operationally before their subtype-sensitive semantics were frozen in the broader research architecture.

## Current IC-022 test

### DISCOVERY

IC-022 classifies the prior “road” failure as:

SEMANTIC TYPE / FRAME FAILURE

It is upstream of:

- package selection;
- dependency reconstruction;
- convergence analysis;
- coverage claims;
- family comparison;
- tool optimization.

Therefore the system must not begin by selecting a large recursive audit package.

### Capability package selected

Minimum sufficient initial package:

1. Task and Object Typing (C01)
2. Referent Continuity Check (C02)
3. Semantic Typing / preflight capability
4. Hidden Dependency Discovery (C07)

Only after these close/open the framing question can the system select deeper structure/evidence/authority capabilities.

This is precisely the capability family the updated Tool Optimization registry is designed to expose.

## Authority-state distinction

The Canonical Authority project contains multiple distinct objects:

- proposition under dispute;
- source claims;
- source authority-status;
- interpretive mechanism;
- truth relevance;
- institutional/legal function;
- case-specific application;
- proposed selector;
- explanations of disagreement.

These cannot be collapsed into one generic “authority” object.

The system must retain OPEN where proposition-specific linkage is absent.

## Sort Later interaction

Potentially useful side discoveries that do not yet have a safe destination may enter Sort Later.

Examples:

- newly discovered historical “road” terminology whose role is unclear;
- a source that might bear on authority but whose proposition-specific relevance has not been established;
- a possible cross-project transfer to another semantic-typing problem.

Known current Canonical Authority findings remain in their project-local destinations.

Sort Later does not become the project state or evidence register.

## Commitment gate

IC-022 may enter COMMITMENT only after:

- target proposition localized;
- project authority frozen;
- relevant domain terms typed or explicitly OPEN;
- protected result declared;
- authorized change/result operation identified;
- acceptance test declared;
- stop condition declared.

This prevents the earlier “road first, type later” failure.

## Expected difference from older workflow

Older workflow:
define/use road
→ build families
→ audit dependencies
→ discover later that roadhood was not fixed.

Updated workflow:
task/object typing
→ semantic preflight
→ test whether “road” has a fixed operational extension
→ keep ROAD OPEN or replace it with typed source/application modules
→ only then construct the downstream dependency/package structure.

## Tool Optimization interaction

Tool Optimization now discovers the capability repertoire from the canonical registry instead of using a hard-coded finite list.

For this project the controller is permitted to select:

FRAME capabilities first,
then STRUCTURE,
then EVIDENCE/FORMAL/TRANSFER/VALIDATION capabilities only where the frozen task state makes them result-sensitive.

A broad package is not selected merely because the project is complex.

## Result

The current architecture catches the prior Canonical Authority failure at a higher layer than the old workflow.

The key gain is not another audit finding.

The gain is that semantic typing is now a prerequisite to the downstream package-selection problem.

## Current disposition

PASS as an architectural stress test.

This run demonstrates improved control selection on the known failure pattern. It does not by itself establish that the resulting research conclusion is correct or that IC-022 is globally superior.
