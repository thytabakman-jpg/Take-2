# Canonical Authority — Target Resolution Experiment 001

Date: 2026-09-24
Status: EXECUTED / FULL C01-C49 COMPARISON
Controller: Improvement Core
Question: Do the same behavior-first capabilities produce the same results when the target is the whole project versus a compressed abstract?

## Frozen goal

G = produce the strongest rigorous source-grounded peer-reviewed Canonical Authority paper while preserving the protected fixed case, method distinctions, boundedness, and reader intelligibility.

## Frozen targets

X_P = whole Canonical Authority project state, including current authoritative research, manuscript, evidence, source, novelty, control, discovery, history, and execution objects.

X_A = ABSTRACT_EXPERIMENT_TARGET.md, a frozen derived abstract of the same current paper state.

For every capability C_i compare:

R_P(i) = C_i(X_P | G)
R_A(i) = C_i(X_A | G)

Classify relation as:

SAME_CORE = same material substantive result survives target compression.
DIFFERENT_RESOLUTION = same capability has useful but materially different yield because target resolution differs.
PROJECT_ONLY = material yield requires project evidence/control/history absent from abstract.
ABSTRACT_STRONGER = abstract exposes communication/compression issue more directly than project-wide target.
NO_MATERIAL_DELTA = capability runs but adds no new material result on that target.

## Aggregate comparison

### Same-core findings

The two targets converge strongly on:
- fixed Rashi-Ramban truth-directed problem;
- native function versus target success;
- source/bridge attribution;
- TRACE / DISCRIMINATE / RECOGNIZE separation;
- package TRACE versus COMPOSE;
- package-level TRACE obstruction;
- boundedness;
- target-relative authority;
- need to qualify corpus and broader significance.

These are representation-robust substantive findings.

### Whole-project-only or project-dominant findings

The whole project uniquely or much more strongly exposes:
- source/provenance status;
- historical supersession;
- corpus-admission registry structure;
- control/authority hierarchy;
- workstream state;
- artifact staleness;
- exact novelty/comparator evidence;
- holdout evidence;
- persistence/consumer routing;
- open/blocked dependencies;
- downstream propagation obligations.

These require information the abstract does not contain.

### Abstract-dominant findings

The abstract more sharply exposes:
- sentence-level density;
- whether every clause earns space;
- compression loss;
- reader-visible order;
- whether scope/admission qualifications arrive before the result;
- whether positive control wording sounds like endorsement or mere methodological possibility;
- whether broader significance appears earned or merely appended.

These are easier to see after project complexity is removed.

## Main experimental result

The outputs are not the same.

A useful approximation is:

R(T,X|G) depends materially on both G and X.

Holding G fixed while changing X changes:
- accessible information;
- resolution;
- admissible transformations;
- verification basis;
- closure strength;
- cost/yield profile.

Therefore goal recovery is necessary but not sufficient for full tool benefit.

A stronger operating form is:

Run(T) = T(X | G, P, V, C)

where:
G = goal,
X = target,
P = protected behavior,
V = verification/observation basis,
C = continuation basis.

## Practical consequence

Do not ask only:
"What tool helps this goal?"

Ask:
"What is the highest-leverage target for this goal, and which tool has the right behavior at that target resolution?"

Whole-project runs are strongest for architecture, evidence, history, provenance, control, and closure.
Abstract runs are strongest for compression, reader experience, claim hierarchy, and visible inferential gaps.
A paired run is valuable when we need both backend correctness and reader-surface quality.
