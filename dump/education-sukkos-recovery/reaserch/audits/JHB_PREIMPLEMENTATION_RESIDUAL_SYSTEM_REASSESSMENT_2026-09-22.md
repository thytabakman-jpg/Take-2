## 1. Universal derived architecture composition view

### PD preflight

Question: would a repository-wide derived composition view materially change the JHB implementation decision or reduce a demonstrated current failure that the existing specialized views cannot handle?

Current controls already provide:

- specialized authority files;
- cross-view interface contracts;
- state-temperature/retrieval rules;
- active-context generation;
- exact-object preflight;
- typed project/goal/artifact/workstream relations.

### Result

A universal view is not required to decide or implement JHB booklet-local ownership.

The JHB use case needs a much narrower derived view: a task-relative booklet workbench that composes JHB root controls with one booklet's local state and artifact/acceptance state.

### Disposition

DEFER universal composition view.
ADD a JHB-specific derived workbench during booklet implementation.

### Reassessment

No prerequisite created. Continue.

## 3. Wider automatic relational/runtime behavior

### PD preflight

Question: would automatic activation, event-generated analytics, or broader relational execution materially reduce current JHB friction without introducing hidden execution or focus loss?

### Result

No.

The current JHB problem is not failure to activate enough automated work. It is making one active booklet's exact local state, artifact lineage, and next permitted action easy to recover.

Automatic cross-system activation would add control complexity without solving that problem and could reactivate precisely the focus-loss failure the current routing architecture prevents.

### Disposition

DEFER. Reopen only after bounded JHB work demonstrates a concrete manual handoff that is both repetitive and safely automatable.

### Reassessment

No prerequisite remains. Continue.

## 5. Compact architecture-decision index

### PD preflight

Question: would a small prospective decision index reduce future reconstruction cost without competing with audits, policies, or authority files?

### Demonstrated need

The current work has already required repeated reconstruction of:

- why JHB is an umbrella;
- why booklet subprojects own local state;
- why CDR remains separate;
- why the Fick pattern can propagate without changing goals;
- why generic system improvements were rejected or deferred.

These are resolved architecture choices with durable future consequences.

### Rival options

A. no index; recover decisions from audits and Git history.
B. full ADR documents for every historical choice.
C. compact non-authoritative prospective index pointing to evidence and authoritative consequences.

B adds excessive backfill and document overhead.
A preserves evidence but imposes repeated recovery cost.
C preserves traceability with the smallest new surface.

### Result

Implement C.

The index must remain navigation/provenance only. It cannot override the policy, goal, state, artifact, or workstream objects that own the consequences.

### Disposition

ADD compact prospective ARCHITECTURE_DECISIONS.yaml and record the current JHB partition decision as its first live entry.

### Reassessment

After implementation, rerun the question: does any remaining system-wide candidate still block JHB? Expected answer: no.
